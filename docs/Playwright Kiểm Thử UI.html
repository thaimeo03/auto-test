01

Playwright là gì?

Hiểu Playwright đang làm gì "phía sau" giúp mọi API sau này có lý do thay vì phải học thuộc lòng.

Playwright là framework kiểm thử tự động hóa trình duyệt mã nguồn mở do Microsoft phát triển. Điểm khác biệt lớn nhất: nó điều khiển thật cả ba engine trình duyệt — Chromium (Chrome/Edge), Firefox và WebKit (Safari) — bằng một API JavaScript/TypeScript duy nhất, không cần driver riêng cho từng trình duyệt như các công cụ đời trước.

Dùng được cho kiểm thử end-to-end giao diện web, kiểm thử API (gọi request trực tiếp không qua UI), và kiểm thử component. Trong tài liệu này, trọng tâm là kiểm thử UI end-to-end với gói @playwright/test.

Cùng một test, chạy độc lập trên cả ba engine nếu cấu hình projects yêu cầu.

02

Cài đặt & khởi tạo dự án

Yêu cầu Node.js bản mới nhất 22.x, 24.x hoặc 26.x. Playwright có sẵn công cụ khởi tạo dự án chỉ với một lệnh.

terminal 
// khởi tạo dự án Playwright Test mới
$npm init playwright@latest

// quá trình cài sẽ hỏi: ngôn ngữ (TypeScript mặc định),
// tên thư mục test (tests/ hoặc e2e/), có thêm GitHub Actions
// workflow không, và có cài sẵn trình duyệt không

// chạy toàn bộ test
$npx playwright test

// chạy có hiển thị cửa sổ trình duyệt
$npx playwright test --headed

// chạy trên một trình duyệt cụ thể
$npx playwright test --project=chromium

Dự án được khởi tạo với cấu trúc: playwright.config.ts ở gốc, thư mục tests/ chứa example.spec.ts mẫu, và package.json/package-lock.json.

Mẹo cho người mới

Chạy npx playwright codegen <url> để mở một cửa sổ trình duyệt: mọi cú click, gõ chữ bạn làm sẽ được Playwright tự sinh thành code, kèm gợi ý locator theo đúng thứ tự ưu tiên (role, text, test-id). Cách nhanh nhất để làm quen mà chưa cần nhớ API.

.env chứa tài khoản/URL môi trường test — luôn thêm vào .gitignore, không bao giờ commit lên repo dù là môi trường test. Dùng biến môi trường của CI (GitHub Actions secrets) để truyền giá trị thật khi chạy trên pipeline.

Quy ước đặt tên nên nhất quán trong cả nhóm: hậu tố .spec.ts cho mọi file test, tên file viết thường nối gạch ngang (login-page.ts), và một file test tương ứng với một luồng nghiệp vụ (ví dụ "đăng nhập") thay vì một trang màn hình — một trang thường được nhiều luồng dùng chung.

04

Cấu trúc một test

Mọi test Playwright đều xoay quanh ba hàm: test(), test.describe() để nhóm, và các hook beforeEach/afterEach.

tests/login.spec.ts 
// import test và expect từ @playwright/test
import { test, expect } from '@playwright/test';

test.describe('Đăng nhập', () => {
  test.beforeEach(async ({ page }) => {
    // chạy trước mỗi test trong nhóm này
    await page.goto('/login');
  });

  test('đăng nhập thành công với tài khoản hợp lệ', async ({ page }) => {
    await page.getByLabel('Tên đăng nhập').fill('thai.tran');
    await page.getByLabel('Mật khẩu').fill('MatKhauDung123');
    await page.getByRole('button', { name: 'Đăng nhập' }).click();

    await expect(page.getByText('Xin chào, Thái')).toBeVisible();
  });
});

Chạy chọn lọc thay vì toàn bộ dự án: npx playwright test login.spec.ts (theo file), npx playwright test --grep "đăng nhập" (theo tên test), hoặc --project=chromium (theo trình duyệt đã khai báo trong config).

05

Locator — cách Playwright tìm phần tử

Locator mô tả cách tìm một phần tử, không phải chính phần tử đó — vì vậy nó luôn "tươi": Playwright tự tìm lại mỗi khi bạn thao tác.

LocatorDùng khi
getByRole('button', {name})Ưu tiên hàng đầu — tìm theo vai trò accessibility, giống cách người dùng và screen reader "nhìn" trang
getByLabel('Mật khẩu')Ô nhập liệu có thẻ <label> đi kèm
getByText('Xin chào')Tìm theo nội dung chữ hiển thị
getByPlaceholder('...')Ô nhập liệu chưa có giá trị, chỉ có placeholder
getByAltText('logo')Hình ảnh, qua thuộc tính alt
getByTitle('...')Phần tử có thuộc tính title
getByTestId('login-btn')Khi không có thuộc tính nào phù hợp — cần gắn data-testid thủ công
Best practice

Ưu tiên locator theo thuộc tính người dùng nhìn thấy (role, label, text) hơn là CSS class hay XPath — class do framework sinh ra (như .css-1x8h2k) đổi bất kỳ lúc nào và làm test vỡ dù giao diện không hề thay đổi hành vi.

Lọc & thu hẹp phạm vi

locator-vi-du.spec.ts 
// chỉ tìm trong khu vực "Giỏ hàng"
const gioHang = page.getByRole('region', { name: 'Giỏ hàng' });
await gioHang.getByRole('button', { name: 'Xóa' }).click();

// lọc theo chữ bên trong
await page.getByRole('listitem').filter({ hasText: 'Sổ tiết kiệm' }).click();

// phần tử đầu tiên / thứ hai trong danh sách trùng khớp
await page.getByRole('row').first().click();
06

Hành động & cơ chế tự động chờ

Trước khi thực hiện gần như mọi hành động, Playwright tự kiểm tra một loạt điều kiện — đây là lý do bạn hiếm khi cần viết sleep thủ công.

Cả năm điều kiện đạt trong vài mili-giây thì hành động chạy ngay; nếu không, Playwright tự chờ tới khi hết thời gian timeout mới báo lỗi.

hanh-dong.spec.ts 
await page.getByRole('button', { name: 'Đăng nhập' }).click();
await page.getByLabel('Email').fill('a@vidu.com');
await page.getByRole('checkbox', { name: 'Ghi nhớ đăng nhập' }).check();
await page.getByLabel('Vai trò').selectOption('Giao dịch viên');
await page.getByRole('link', { name: 'Trợ giúp' }).hover();
await page.getByLabel('Ảnh đại diện').setInputFiles('avatar.png');
await page.keyboard.press('Enter');
Tránh

Đừng dùng page.waitForTimeout(3000) (chờ cứng theo mili-giây) để "cho chắc". Nó vừa làm test chậm không cần thiết, vừa không đáng tin — hãy để auto-wait và assertion tự lo việc chờ.

07

Assertion — kiểm tra kết quả

Assertion của Playwright Test là "web-first": chúng tự chờ và thử lại cho tới khi điều kiện đúng hoặc hết timeout (mặc định 5 giây), thay vì kiểm tra một lần rồi báo lỗi ngay.

AssertionKiểm tra
toBeVisible()Phần tử đang hiển thị trên trang
toHaveText('...')Nội dung chữ khớp chính xác hoặc theo mẫu
toHaveValue('...')Giá trị hiện tại của ô nhập liệu
toHaveCount(3)Số lượng phần tử khớp với locator
toHaveScreenshot()So sánh ảnh chụp với ảnh tham chiếu (visual regression)
assertion.spec.ts 
await expect(page.getByRole('alert')).toBeVisible();
await expect(page.getByTestId('so-du')).toHaveText('1.250.000đ');
await expect(page.getByRole('listitem')).toHaveCount(5);

// soft assertion: ghi nhận lỗi nhưng vẫn chạy tiếp test,
// hữu ích khi muốn thấy nhiều lỗi cùng lúc thay vì dừng ở lỗi đầu tiên
expect.soft(await page.title()).toBe('Trang chủ');
✓ đăng nhập thành công với tài khoản hợp lệ (842ms)
✕ hiển thị lỗi khi sai mật khẩu (1204ms)
Expected: "Sai tên đăng nhập hoặc mật khẩu"
Received: "" (phần tử alert chưa xuất hiện trong 5000ms)
08

Fixture & Page Object Model

Hai kỹ thuật này giải quyết cùng một vấn đề: tránh lặp lại code setup và selector rải rác khắp các file test.

Fixture có sẵn

page (trang biệt lập cho mỗi test), context (BrowserContext chứa page), browser (dùng chung giữa các test), browserName, và request (gọi API không qua UI) đều được Playwright Test tự cung cấp — chỉ cần khai báo trong tham số của test().

Page Object Model (POM)

Gom selector và thao tác của một trang vào một class — test đọc như mô tả hành vi nghiệp vụ, còn chi tiết locator nằm gọn một chỗ, đổi giao diện chỉ cần sửa một file.

pages/login-page.ts 
import { type Locator, type Page } from '@playwright/test';

export class LoginPage {
  readonly page: Page;
  readonly username: Locator;
  readonly password: Locator;
  readonly submitBtn: Locator;

  constructor(page: Page) {
    this.page = page;
    this.username = page.getByLabel('Tên đăng nhập');
    this.password = page.getByLabel('Mật khẩu');
    this.submitBtn = page.getByRole('button', { name: 'Đăng nhập' });
  }

  async goto() {
    await this.page.goto('/login');
  }

  async loginAs(user: string, pass: string) {
    await this.username.fill(user);
    await this.password.fill(pass);
    await this.submitBtn.click();
  }
}

Kết hợp POM với fixture tùy chỉnh

fixtures.ts 
import { test as base } from '@playwright/test';
import { LoginPage } from './pages/login-page';

export const test = base.extend<{ loginPage: LoginPage }>({
  loginPage: async ({ page }, use) => {
    const loginPage = new LoginPage(page);
    await loginPage.goto();
    await use(loginPage);
  },
});

Trong file test, import test từ fixtures.ts thay vì trực tiếp từ @playwright/test — nhờ vậy tham số loginPage đã có sẵn, không cần khởi tạo lại ở mỗi test.

09

Giả lập mạng (network mocking)

Best practice của Playwright: không kiểm thử dựa vào dịch vụ bên thứ ba bạn không kiểm soát — hãy giả lập response để test ổn định và nhanh.

network.spec.ts 
// giả lập một API trả về dữ liệu tùy ý, không gọi server thật
await page.route('**/api/so-du', route => route.fulfill({
  status: 200,
  contentType: 'application/json',
  body: JSON.stringify({ soDu: 1250000 }),
}));

// chặn tải ảnh để test chạy nhanh hơn
await page.route('**/*.{png,jpg,jpeg}', route => route.abort());

await page.goto('/tai-khoan');
await expect(page.getByTestId('so-du')).toHaveText('1.250.000đ');

Có thể gắn route() ở cấp page (chỉ áp dụng cho trang đó) hoặc cấp context (áp dụng cho mọi trang được mở từ context đó). Dùng page.waitForResponse('**/api/so-du') khi cần chờ đúng một response cụ thể hoàn tất trước khi assert.

10

Debug & Trace Viewer

Khi test fail, ba công cụ này trả lời câu hỏi "chuyện gì đã xảy ra" nhanh hơn nhiều so với đọc log text.

UI Mode — chế độ xem trực quan khi viết test

terminal 
$npx playwright test --ui

Mở giao diện xem danh sách test theo file, chạy từng test riêng lẻ, xem "time travel" từng bước hành động kèm ảnh chụp DOM, tab network, console log, và công cụ "pick locator" để thử selector trực tiếp trên trang — kèm chế độ watch tự chạy lại khi code đổi.

Trace Viewer — điều tra sau khi test đã chạy xong

terminal 
// buộc ghi trace ở lần chạy local tiếp theo
$npx playwright test --trace on

// mở báo cáo HTML sau khi test chạy xong
$npx playwright show-report

Mặc định trong config, trace: 'on-first-retry' — chỉ ghi trace khi một test fail và được retry, tiết kiệm dung lượng mà vẫn có dữ liệu để điều tra khi cần. Trace Viewer cho xem lại từng hành động theo dòng thời gian, DOM snapshot trước/sau mỗi bước, network và console log đi kèm.

11

Chạy trên CI: GitHub Actions

Khi khởi tạo dự án, Playwright có thể tự sinh sẵn một workflow GitHub Actions — không cần viết từ đầu.

.github/workflows/playwright.yml 
name: Playwright Tests
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
jobs:
  test:
    runs-on: ubuntu-latest
    timeout-minutes: 60
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 24 }
      - run: npm ci
      - run: npx playwright install --with-deps
      - run: npx playwright test
      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: playwright-report
          path: playwright-report/
          retention-days: 30

Workflow chạy trên Ubuntu (rẻ và nhanh hơn macOS/Windows trên CI), giới hạn 60 phút, và luôn tải lên báo cáo HTML dù test pass hay fail để xem lại trên tab Actions của GitHub.

Lưu ý bảo mật

Trace, báo cáo HTML và console log có thể chứa dữ liệu nhạy cảm (token, thông tin request/response thật). Chỉ lưu artifact ở nơi tin cậy, đặc biệt với repo private của ngân hàng hay dữ liệu khách hàng.

12

Cấu hình nâng cao: playwright.config.ts

Một file cấu hình kiểm soát mọi thứ: chạy trên trình duyệt nào, chạy song song bao nhiêu luồng, có retry hay không, và URL gốc của ứng dụng.

playwright.config.ts 
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  testDir: 'tests',
  fullyParallel: true,
  retries: process.env.CI ? 2 : 0,
  workers: process.env.CI ? 1 : undefined,
  reporter: 'html',
  use: {
    baseURL: 'http://localhost:3000',
    trace: 'on-first-retry',
  },
  projects: [
    { name: 'chromium', use: { ...devices['Desktop Chrome'] } },
    { name: 'firefox', use: { ...devices['Desktop Firefox'] } },
    { name: 'webkit', use: { ...devices['Desktop Safari'] } },
  ],
  webServer: {
    command: 'npm run start',
    url: 'http://localhost:3000',
    reuseExistingServer: !process.env.CI,
  },
});

Với baseURL đã khai báo, mọi page.goto('/login') trong test tự nối thành URL đầy đủ. webServer tự khởi động ứng dụng trước khi chạy test — tiện khi CI chưa có sẵn môi trường đang chạy. Trên máy cá nhân nên để workers mặc định (song song tối đa); trên CI thường giới hạn để tránh quá tải runner dùng chung.

13

Quy trình thực chiến: viết test đăng nhập từ A-Z

Gộp toàn bộ phần trên thành một kịch bản hoàn chỉnh — dùng để demo trực tiếp cho người mới, từng bước một.

Cài đặt & khởi tạo dự án

npm init playwright@latest, chọn TypeScript, đồng ý cài trình duyệt và thêm GitHub Actions workflow.

Khám phá trang bằng codegen

npx playwright codegen localhost:3000/login — đăng nhập thử bằng tay, xem Playwright gợi ý locator nào cho từng ô.

Viết test đầu tiên, thô nhưng chạy được

Copy code từ codegen vào tests/login.spec.ts, chạy thử bằng npx playwright test --ui để xem trực quan từng bước.

Dọn lại locator theo best-practice

Thay các locator do codegen sinh (đôi khi là CSS) bằng getByRole/getByLabel nếu có thể — bền hơn khi giao diện đổi.

Thêm assertion & test cho trường hợp lỗi

Viết thêm một test đăng nhập sai mật khẩu, assert thông báo lỗi hiển thị đúng — không chỉ test đường "happy path".

Tách thành Page Object

Chuyển selector và thao tác sang LoginPage, để file test chỉ còn đọc như một kịch bản nghiệp vụ.

Bật trace & chạy đa trình duyệt

npx playwright test --trace on, kiểm tra chạy được trên cả ba projects đã khai báo trong config.

Đẩy lên CI

Commit workflow GitHub Actions đã sinh sẵn, mở Pull Request, xác nhận test chạy xanh trên tab Actions trước khi merge.

14

Bài tập thực hành

6 bài, từ dễ đến khó, thực hành trên demo.playwright.dev/todomvc — trang demo chính thức của Playwright, luôn online, không cần dựng server riêng. Tự làm trước, bấm "Xem gợi ý" chỉ khi bí.

01

Thêm một công việc

Dễ

Viết test mở trang TodoMVC, gõ "Mua sữa" vào ô nhập rồi nhấn Enter, sau đó assert công việc đó xuất hiện trong danh sách.

Xem gợi ý code
bai-tap-01.spec.ts 
import { test, expect } from '@playwright/test';

test('thêm một công việc mới', async ({ page }) => {
  await page.goto('https://demo.playwright.dev/todomvc/');

  const oInput = page.getByPlaceholder('What needs to be done?');
  await oInput.fill('Mua sữa');
  await oInput.press('Enter');

  await expect(page.getByTestId('todo-title')).toHaveText('Mua sữa');
});
02

Thêm nhiều công việc & đếm số lượng

Dễ

Thêm 3 công việc khác nhau bằng một vòng lặp, assert getByTestId('todo-item') có đúng 3 phần tử.

Xem gợi ý code
bai-tap-02.spec.ts 
const input = page.getByPlaceholder('What needs to be done?');

for (const viec of ['Mua sữa', 'Dọn nhà', 'Học Playwright']) {
  await input.fill(viec);
  await input.press('Enter');
}

await expect(page.getByTestId('todo-item')).toHaveCount(3);
03

Đánh dấu hoàn thành & đọc bộ đếm

Trung bình

Từ danh sách 3 công việc ở bài 02, tick checkbox của công việc đầu tiên, assert chữ "2 items left" hiển thị đúng.

Xem gợi ý code

await page.getByTestId('todo-item').first().getByRole('checkbox').check();

04

Lọc danh sách theo trạng thái

Trung bình

Sau bài 03, bấm liên kết lọc "Active" rồi "Completed" (getByRole('link', { name })), assert đúng số lượng hiển thị ở từng chế độ.

Xem gợi ý code

await page.getByRole('link', { name: 'Active' }).click();

await page.getByRole('link', { name: 'Completed' }).click();

05

Refactor thành Page Object

Nâng cao

Gom bài 01-04 vào một class TodoPage với các method goto(), addTodo(text), items(), completeFirst() — file test chỉ còn gọi method, không còn locator thô.

Xem gợi ý code
pages/todo-page.ts 
import { type Page } from '@playwright/test';

export class TodoPage {
  constructor(private page: Page) {}

  async goto() {
    await this.page.goto('https://demo.playwright.dev/todomvc/');
  }

  async addTodo(text: string) {
    const input = this.page.getByPlaceholder('What needs to be done?');
    await input.fill(text);
    await input.press('Enter');
  }

  items() {
    return this.page.getByTestId('todo-item');
  }

  async completeFirst() {
    await this.items().first().getByRole('checkbox').check();
  }
}
06

Thử thách: giả lập lỗi mạng trên dự án của bạn

Thử thách

Bài này không dùng TodoMVC. Chọn một màn hình trong dự án SCH (hoặc dự án cá nhân) có gọi API, dùng page.route() để giả lập response lỗi 500, rồi assert thông báo lỗi tiếng Việt hiển thị đúng cho người dùng. Không có đáp án mẫu cố định vì phụ thuộc API thật của bạn — tự kiểm tra theo checklist bên dưới.

  • Route đúng URL pattern của API cần giả lập, không chặn nhầm request khác
  • Response trả về đúng status lỗi (500 hoặc mã ứng dụng thật sự trả)
  • Assert thông báo hiển thị đúng nội dung tiếng Việt, không phải lỗi mặc định của trình duyệt
  • Test không cần server thật đang chạy để tái hiện được lỗi này

16

Lỗi thường gặp & mẹo nhỏ

Những điều người mới học Playwright hay vấp phải nhất — nhắc trước để đỡ mất công gỡ lỗi sau.

Hay gặp

Quên await trước lệnh Playwright — mọi API đều trả về Promise. Thiếu await khiến hành động "chạy" nhưng test không thực sự chờ, dẫn tới lỗi khó hiểu ở dòng sau.

Hay gặp

Dùng selector giòn như nth-child(3) hoặc class do framework tự sinh — chỉ cần đổi thứ tự phần tử hoặc build lại CSS là test vỡ dù ứng dụng vẫn đúng.

Hay gặp

Các test phụ thuộc lẫn nhau (test B cần test A chạy trước để có dữ liệu) — vi phạm nguyên tắc cô lập (test isolation), khiến việc chạy song song hoặc chạy riêng lẻ một test bị lỗi sai.

Mẹo

Viết test trước bằng UI Mode (--ui) để thấy ngay lỗi locator hoặc lỗi luồng, thay vì chạy headless rồi đoán qua log text.

Mẹo

Giữ Playwright luôn cập nhật (npm install -D @playwright/test@latest) — mỗi bản mới đi kèm bản build trình duyệt mới nhất, giảm khác biệt hành vi so với người dùng thật.
